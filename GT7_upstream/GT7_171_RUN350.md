## The two local-save patches are correct, including `mov eax, 4`

Byte diff of the live eboot against `eboot.bin.orig`: 15 bytes in exactly two
runs, nothing else.

| file offset | VA | original | now | |
|---|---|---|---|---|
| `0x0176AB60` | `0x1766B60` | `8a 46 08 24 02 d0 e8` | `31 c0 c3 90 90 90 90` | `xor eax,eax ; ret` |
| `0x0176D6C0` | `0x17696C0` | `55 48 89 e5 41 57 41 56` | `b8 04 00 00 00 c3 90 90` | `mov eax,4 ; ret` |

These are the 1.71 equivalents of P2 and P1 in `C:\GT7_offline\gt7save.py`. P1 on
1.00 writes `mov eax, 2` (USELOCAL), so the `4` looked like a transcription
error. It is not. Static analysis, emulator closed, reads only:

- `0x17696C0` is the server handshake and has exactly ONE caller, at
  `0x17646B1`, inside the function beginning at `0x1764600`.
- That function names itself through a string it logs:
  `BatchQueue::init data_->initialize() resetLocal=true`.
- Its return value IS the `IsOnline()` expression `gt7save.py` documents:
  `mov al,[rbx+0x11] ; setne al ; cmp dword [rbx+0x14],0 ; setg cl ; and al,cl ; ret`.
- In 5056 bytes there is **exactly one** write of the status field:
  `mov dword ptr [rbx+0x14], r15d` at `0x1764713`.

1.71 branches on the returned status - the 1.00 note that "the retail script does
not branch on the status at all" does not hold here:

```
0x17646C2  cmp r15d, 2 ; sete r12b     is it USELOCAL
0x17646CA  cmp r15d, 4 ; jne 0x1764D2D only 4 falls through toward the store
0x17646E6  mov r15d, 4                 re-affirmed, then stored
```

- status 4 takes the short path to the store; `IsOnline = online && 4 > 0`.
- status 1/2/3 reach `0x1764D2D` (`lea ecx,[r15-1] ; cmp ecx,2 ; ja 0x176544B`)
  and land in a block that builds format arguments from the status itself and
  logs `resetLocal=true`, i.e. re-initialisation with a local reset.
- status 0 or >= 5 go to the error tail at `0x176544B`.
- Storable statuses are 4 (direct), 3 (`0x1765113` then `jmp 0x17646EF`) and
  **-1** (`0x1764B7B`) - and `setg` is signed, so -1 makes `IsOnline` false.

**Porting 1.00's `mov eax, 2` to 1.71 would route the game into the resetLocal
path.** 4 is the only value that reaches the store without passing through
re-initialisation or the error tail.

The other half of the gate does not depend on the online patches:
`[+0x11]` comes from the automation startup file. `app_param_0.sfo` was verified
present at SHA256 `d7319018a60a11ec87ac713eae6d397a829ee6c5dfb4dd068bec4107a1473024`,
which matches the launcher's own reference value. So the save-only state is not
merely a diagnostic - it is a candidate configuration.

## `run_gt7_171.ps1`: the whitelist, and three smaller corrections

Removing the seven online patches produced an eboot the launcher had never seen,
and it refused to start: *"The 1.71 eboot differs from the verified patch sets."*
The guard behaved correctly; the whitelist was incomplete.

- Added `$saveOnlyHash` with a comment recording what the state is and that it
  was byte-verified against `eboot.bin.orig`.
- `-RequireLocalSave` demanded the old combined hash, so it would have rejected
  a state that does contain the local-save patches. It now accepts either.

  including when that was false. It now reports the measured state and prints
  `Online sign-in patch:` and `Local-save experiment:` separately.
- The run manifest gained `onlineSignInPatch` and `ebootState`.

## The 1.71 index: two constants recovered, the key is not

`gt.idx` on 1.71 does not open with the 1.00 constants. The reason is now known
and it is not only the key - the magic and the header-layer seed both changed.

| | 1.00 | 1.71 |
|---|---|---|
| index magic | `0x5B745163` ("cQt[") | **`0x122BB8F2`** |
| header-layer CRC seed | `0xA7E4A1E8` | **`0x1FD5B434`** |
| CRC-32 table (poly `0x04C11DB7`) | va `0x477AFE4` | va `0x46471A0` (unchanged content) |

Located by reading the code, not by searching for bytes:

- `/contents/gt.idx` is named by a LEA at `0x3177F2F`; that function mounts the
  MPH filesystem and hands off through a vtable.
- The index loader is the function at `0x317FBD0`. It calls `0x3181700`
  (open, read, decrypt), then `0x317C1C0`, then
  `cmp dword ptr [r15], 0x122BB8F2` at `0x317FC5D`.
- `0x317C1C0` is `decrypt_header_layer`: same CRC table, same four-step chain,
  same `not`, same `0x800` span, and `mov r8d, 0x1FD5B434` at `0x317C1C3`.

Where the keys live. They are pre-built ChaCha20 state blocks, each preceded by
the sigma constant `expand 32-byte k`, reached from a pointer table of 0x18
stride:

```
1.00  file 0x5E8E308  IDX_IV       0x5E8E310 sigma  0x5E8E320 DATA_KEY
      file 0x5E8E340  sigma        0x5E8E350 IDX_KEY
1.71  file 0x579CE00  sigma        0x579CE10 DATA_KEY  (byte-identical to 1.00)
      file 0x579CDC0  16 bytes that are NOT sigma - table entry [3] points here,
                      where 1.00's entry [3] points at the second sigma
```

So 1.71's index key is obscured rather than simply moved: the sigma that marks
it is absent, and a candidate sweep of that whole neighbourhood (272 key offsets
x 298 IV candidates) found nothing.

WARNING: **That negative result is void.** It was run against 1.00's magic, before the
loader had been read, so the oracle could not have returned a positive whatever
the input. It must be repeated with `0x122BB8F2` / `0x1FD5B434`.

The oracle is cheap and worth reusing: only the first word is needed, so the
0x800-byte CRC chain collapses to its i=0 step, `plain0 = ~(V0 ^ word0)` with
`V0 = f(seed)`. One ChaCha20 block per candidate. Run the control on 1.00 first -
a sweep whose control cannot pass is not a measurement.

WARNING: Tool caveat for `C:\GT7_offline\gt7func.py`: its call-target cache is built
from every `e8` byte read as `call rel32`, so it emits false entries. It reported
the index loader's entry as `0x317FB8C`, which decodes as garbage; the real
prologue is at `0x317FBD0`, found by scanning back for `55 48 89 e5`.
